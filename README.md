# Khmer AI-Text Detector

A binary classifier that decides whether a Khmer text was **written by a person (label 0)** or **generated by an AI (label 1)**. The project also builds the dataset it needs: no public Khmer human-vs-AI dataset existed. The dataset, model and report will be published on Hugging Face and GitHub.

This README is also the project's living journal. It records the tools used and why, the purpose of each step, how each step works, and every issue met along the way (technical and non-technical). It is updated after each step.

## Why this project

- Khmer is a low-resource language. Most AI-text detectors are built for English and are not expected to work well on Khmer.
- No public dataset of Khmer human-written and AI-generated text existed, so this project builds one.
- The goal is a careful, honest detector. That means matching topics and lengths between the two classes so the model cannot cheat on easy clues, and testing it on an AI model it never saw in training.

## Pipeline

### Step 1. Collect human text (done)

**Purpose.** The classifier needs texts that are surely human. Texts written before ChatGPT was released (30 Nov 2022) are very unlikely to contain AI writing.

**How it works.** Passages are taken from two sources, with a quota of 4,000 per source:

- Khmer Wikipedia.
- mC4 Khmer web news (pages crawled 2013-2020).

Passages are kept at 300-2,500 characters.

**Files.** `notebooks/01_collect_human_text.ipynb` (run locally); output `data/human.csv`.

**Results.** 7,964 passages: Wikipedia 3,969 and mC4 web news 3,995. Length 300-2,500 characters, mean about 1,484.

**Limitations.**

- VOA Khmer was skipped (SSL error); mC4 already includes about 147 `khmer.voanews.com` passages.
- The Wikipedia dump is from Nov 2023, so a few articles may have been edited with AI help.

### Step 2. Generate AI text (in progress)

**Purpose.** For every human passage, an AI model writes a Khmer text on the same topic and at about the same length. This gives the second class.

- **Why topic-matched:** so the classifier cannot learn "this topic means AI". Only the writing style should differ.
- **Why four models:** different models write differently. One of them (qwen) is held out of training to test whether the detector works on an AI model it has not seen.

**How it works.**

- The prompt asks for a text of the target length (plus or minus 20%) at temperature 0.8 (a setting that makes output a bit varied).
- There are two prompt types: `wiki_title` (Wikipedia: the model is given the article title) and `web_hint` (news: the model is given the first 200 characters as a topic hint).
- Four generators, assigned round-robin after a shuffle with seed 42:
  - `gemini-3.1-flash-lite` and `gemma-4-31b-it` (Gemini API)
  - `openai/gpt-oss-120b` and `qwen/qwen3.8-27b` (Groq)
- Only the 7,230 passages that survive step-3 cleaning get an AI partner (about 1,807 per generator).
- The assignment is frozen in `data/generated/plan.jsonl`.
- `data/generated/ai_raw.jsonl` is append-only and doubles as the checkpoint. Reruns skip finished rows. Errors go to `ai_errors.jsonl`; the log is `full_run.log`.
- `src/run_generation.ps1` reruns the resumable script every 30 minutes until it prints "Nothing to do".

**Files.** `src/generate_ai.py`, `src/run_generation.ps1`.

**Progress.** On 2026-10-29: 2,551 of 7,230 done (flash-lite 1,311, gpt-oss 562, gemma 415, qwen 263). gpt-oss adds about 110 texts a day, so about 12 more days are expected; its daily quota is the bottleneck.

### Step 3. Clean and length-match (script ready)

**Purpose.** Human and AI texts must differ only in style. Any leftover structural difference (footers, odd spacing, cut-off endings, different lengths) lets a model score well without learning anything useful.

**How it works.** The same rules are applied to both classes:

- Strip invisible characters (for example the zero-width space U+200B, which gpt-oss adds).
- Strip Wikipedia footer sections (See also, References, external links, notes, categories), list markers, title/URL/wikitext lines and short fragment lines.
- Remove spaces before Khmer punctuation marks (U+17D4-U+17D6).
- Trim each text to its last sentence end.
- Drop texts that are low in Khmer characters (under 70%), too short (under 300) or too long (over 2,500), AI texts that copy the hint, and duplicates.
- Length-match human and AI texts per 200-character bin (seed 42), preferring human passages whose AI partner is kept.

**Files.** `src/clean.py`; output `data/processed/clean.jsonl` and `reports/step3_clean_stats.json`.

**Known leftover.** Some mC4 passages still contain inline site-navigation text (for example "- Kampuchea Thmey Home ...").

### Step 4. Split (script ready)

**Purpose.** To measure honestly, test data must be unseen, and one AI model must never appear in training.

**How it works.**

- `qwen/qwen3.8-27b` is held out as `test_ood`. OOD means out-of-distribution: data from a source the model did not train on. It is balanced with humans per length bin.
- The rest is split 80/10/10 into train, validation (val) and test, stratified by pair type, generator and source so every split has the same mix.
- Splits are grouped by `human_id`, so an AI text and its human source always land in the same split.

**Files.** `src/split.py`; output `data/processed/splits/*.jsonl` and `reports/step4_split_stats.json`.

### Step 5. Baseline (script ready)

**Purpose.** A simple model sets the bar. A big model that cannot beat it is not worth its cost. The baseline also exposes shortcut features.

**How it works.** TF-IDF turns text into numbers by counting how often short pieces occur, weighted by how distinctive they are. Here the pieces are character n-grams of length 1-4. A logistic regression (a simple linear classifier) is trained on them. The regularisation strength C is tuned on val (best C = 10). The script also prints the top n-grams per class, to catch shortcuts.

**Files.** `src/baseline.py`.

### Step 6. Fine-tune XLM-RoBERTa (ready; run once on partial data)

**Purpose.** Test whether a pretrained multilingual language model beats the baseline. Fine-tuning means continuing the training of an already trained model on this task.

**How it works.** `xlm-roberta-base` is trained for 3 epochs with learning rate 2e-5, batch size 16 and a maximum of 512 tokens. The best checkpoint is chosen by val F1. Training took 150 seconds on a Colab T4 (2026-10-26, 1,404 train rows).

**Colab route.**

1. `python src/make_colab_bundle.py` builds `colab_bundle.zip` (code plus splits; gitignored).
2. Drag it into the root of My Drive.
3. Open `Colab Notebooks/02_finetune_xlmr.ipynb` from Drive, pick the T4 GPU and choose Run all.
4. Outputs land in Drive under `khmer-ai-text-detector/`.

**Files.** `src/finetune.py`, `notebooks/02_finetune_xlmr.ipynb`, `src/make_colab_bundle.py`. Results are in `reports/step6_xlmr_*`.

**Note.** If the notebook is used with `CODE_SOURCE = "github"` while the repo is private, set `USE_TOKEN = True` and add a `GITHUB_TOKEN` secret.

Report F1 and ROC-AUC, results per generator, and robustness to paraphrasing and truncation. ROC-AUC measures how well the model ranks AI texts above human ones, regardless of the threshold; F1 balances precision and recall. The truncation question from step 6 (see Results) will be checked here.

## Results so far

> **Warning: these numbers are from partial data and are not final.** They use only 920 AI rows (train 1,404 / val 175 / test 175 / test_ood 56). Scores this close to perfect on so little data probably mean the task is still too easy or that shortcut features remain. Steps 3-6 must be rerun on the full data before any of this is trusted.

| Model | val F1 | test F1 | test_ood F1 | ROC-AUC val / test / ood |
|---|---|---|---|---|
| TF-IDF + logistic regression | 0.977 | 0.989 | 1.000 | 0.996 / 0.999 / 1.000 |
| XLM-RoBERTa base | 0.951 | 0.978 | 0.949 | 0.994 / 0.998 / 1.000 |

Observations:

- XLM-R scored a bit below the TF-IDF baseline.
- Almost all XLM-R errors are human texts called AI: val 9 false positives and 0 false negatives, test 3 and 1, ood 3 and 0.
- At 512 tokens about half the texts are truncated (train 55%), humans more often than AI (about 59% vs 50%), because Khmer uses many tokens per text. To be checked in step 7.

## How to run

From the repository root, on Windows:

```powershell
python -m venv .venv
.venv\Scripts\pip install -r requirements.txt
```

Create a `.env` file with `GEMINI_API_KEY` and `GROQ_API_KEY`.

Step 2 (generation, in its own window), and how to watch it:

```powershell
powershell -ExecutionPolicy Bypass -File src\run_generation.ps1
Get-Content data\generated\full_run.log -Wait -Tail 5
```

Steps 3-5 and tests:

```powershell
python src/clean.py
python src/split.py
python src/baseline.py
python -m pytest tests
```

Step 6:

```powershell
python src/make_colab_bundle.py
```

Then drag `colab_bundle.zip` to the root of My Drive, open `02_finetune_xlmr.ipynb` in Colab, select the T4 GPU and choose Run all. Outputs land in Drive under `khmer-ai-text-detector/`.

### Record schema

Each record has: `text, label, source, generator, url, date, length`.

### Conventions

- Labels are integers: `0` = human, `1` = ai.
- Python 3.10+; dependencies in `requirements.txt`.
- Data is saved as UTF-8 JSONL or CSV; Khmer text must round-trip without mojibake (garbled characters).
- Fixed random seed 42 for all splits and sampling.
- Human-text quota is 4,000 per source.
- Respect API rate limits: retry with backoff and resume from checkpoints.
- After each step, report counts, the length distribution and a few random samples.
